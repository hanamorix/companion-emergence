# 1.5 — Criteria (#158)

Labeled gating/advisory accept bar. "Done" rests on conformance (no regression workload exists
for this project — see the Layer-2 config).

## Gating

- **G1 (negative / core false-positive fix — the mtime-only bump is silent).** Inside a real
  `sandbox()` run, an **mtime-only bump with identical bytes** of `~/.claude/policy-limits.json`
  and `~/.claude/remote-settings.json` (the exact empirical churn: `os.utime` to a later mtime,
  content unchanged) under a monkeypatched fake `~/.claude` produces a **clean exit**: NO
  `SandboxLeak` raised AND NO `RuntimeWarning` emitted. This is the bug being killed.
  - Oracle-can-fail preface: a **no-exclude / mtime-sensitive** `_fingerprint(claude,
    hash_content=True)` before/after the same bump DIFFERS (proves the churn would trip pre-fix).

- **G1b (positive / content-aware — a genuine content change to the two files STILL warns).**
  Inside a real `sandbox()` run, a **content rewrite** of `policy-limits.json` (or
  `remote-settings.json`) — different bytes → different `sha256` — STILL surfaces as a
  `RuntimeWarning` matching "DOWNGRADED to a warning" (a `~/.claude`-only diff). This is the
  detection floor the content-aware design preserves: only the mtime axis is silenced, not the
  content axis. (This is the property a full name-prune could not have; it is now testable.)

- **G2 (positive / not blinding — a non-housekeeping `~/.claude` file still surfaces).** Inside a
  real `sandbox()` run, mutating a **non-housekeeping** `~/.claude` file (e.g. `settings.json`)
  still triggers the guard's reaction under current semantics — a `RuntimeWarning` matching
  "DOWNGRADED to a warning". Proves the mtime-insensitivity is scoped to the two named files, not
  one path broader / not blanket `~/.claude`.

- **G3 (positive / oracle can still hard-raise).** The change does not weaken hard detection of a
  real escape to a **non-`~/.claude`** guarded root: such a mutation still raises `SandboxLeak`
  (covered by the existing negative-control tests; assert they remain green, and add a case where
  the two housekeeping files churn *alongside* a real non-`~/.claude` escape and it still raises).

- **G4 (targeted, fail-closed elsewhere).** Only the two named top-level files are made
  mtime-insensitive. A **third**, non-named top-level `~/.claude` `*.json` (e.g.
  `some-other.json`) written in the same run is still seen (surfaces as the option-(c) warning).
  No blanket `~/.claude` prune.

- **G4b (top-level only — same-basename in a subdir stays fully guarded).** A same-basename file
  in a `~/.claude` **subtree** (e.g. `~/.claude/plugins/policy-limits.json`) keeps its normal
  **mtime-sensitive** entry: an mtime-only bump of *that* file is still detected (the match is by
  exact resolved top-level path, not basename-anywhere).

- **G5 (the new constant is pinned).** The new CLI-housekeeping constant contains exactly
  `("policy-limits.json", "remote-settings.json")` and the helper that derives their absolute
  paths returns exactly those two under `~/.claude` — asserted by a test, so a silent
  narrowing/widening is caught (mirrors `test_af2_exclusion_set_unchanged`).

- **G6 (session-log allowlist unchanged).** `_CLAUDE_SESSION_LOG_DIRS` and
  `_CLAUDE_SESSION_LOG_FILES` literals are **unchanged** (the housekeeping files go in their own
  constant and their own `mtime_insensitive` path, NOT the exclude list), so
  `test_af2_exclusion_set_unchanged` stays valid and the semantic distinction (session logs vs
  server-pushed config) is preserved.

- **G7 (semantics unchanged).** No change to the raise-vs-warn logic in the post-run block; the
  option-(c) downgrade condition (`changed == [str(claude_root)]`) is untouched. The change is
  confined to what `_fingerprint` records for two files (dropping the mtime slot, keeping the
  content hash) — a detection-scope change, not a response-semantics change. Verified by diff
  review + the existing downgrade/scope tests staying green.

## Advisory

- **A1.** The fix comment states the *real* safety argument for these two files (server-managed
  CLI config, guaranteed per-run churn, no companion write-motive; residual risk within the
  owner-accepted option-(c) envelope) rather than borrowing the F4 "Canary-provably-cannot-write"
  argument verbatim (which the option-(c) note itself qualifies).

## Verification method

  `tmp_path`) — the real developer `~/.claude` is never touched by the suite.
- CI: `uv run ruff check .` clean; `uv run pytest -m "not live and not requires_claude_cli and
  not integration" -q` green **except** the two known out-of-scope failures
  (`test_review_tick_gate_blocks_send_records_hold` #136, `test_history_returns_buffered_turns_in_order`
  #155). Any other failure is in scope.

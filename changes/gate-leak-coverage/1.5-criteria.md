# 1.5 — Criteria (the accept bar)

All criteria are **gating** unless labeled advisory. Each is checkable by execution at
stage 8 (pytest). Oracles must be shown able to fail (ST1.5f): each new test is demonstrated
to fire against the pre-change / known-violating state.

## G1 — reconcile routed (per-site, positive assertion)
Calling the real `brain/self_model/reconcile.py` reconcile-memory write against a temp
persona results in a `self_model_reconcile` candidate in `pending_candidates.jsonl` and
**zero** `self_model_reconcile` rows in `memories.db`.
*Oracle:* drive the actual function; assert queue has the type, DB has zero. *Shown-able-to-fail:*
the same assertion run against the pre-change function (direct `store.create`) must FAIL (row
lands in DB, no queue file). Recorded in stage 8.

## G5 — LIVE-PATH integration: the gate demonstrably FIRES end-to-end (positive)
Exercising the real per-turn write path in-process against a fresh temp persona:
- the monologue capture path — `brain/chat/monologue_capture.py::capture_monologue`
  (the actual handler dispatched for the `record_monologue` tool call at
  `brain/tools/dispatch.py:186`) → `write_trace_memory`; AND
- the pass-2 apply path — driven through the **public** wrapper the live pass-2 worker
  actually calls, `brain/chat/extractor.py::apply_side_effects(ExtractorOutput(memory_writes=…,
  emotion_delta=…), persona_dir=…)` (invoked at `brain/chat/tool_loop.py:78`), NOT the private

Result: `pending_candidates.jsonl` is **created and non-empty**, with **zero** rows of any

*Not marked `integration`/`live`/`requires_claude_cli`* — it must run in the default CI
selection (both functions are pure Python with no provider call in their write path).
*Shown-able-to-fail:* the assertion fails against a direct-`store.create` stand-in
(demonstrated in the test module via an ungated write).

## G6 — direct-write coverage guard (catches future leaks; fails safe on novel receivers)
A test enumerates **every** line matching `\.create\(` under `brain/**/*.py` (this matches
`store.create(`, `mem_store.create(`, `soul_store.create(`, and any other receiver's
`.create(`; it does NOT match `Memory.create_new(` — different method) and asserts that set is
a **subset of a pinned union of two lists**:
1. **KNOWN-NON-MEMORY `.create(` (excluded — not memory-store writes):** the `pending.create(`
   calls in `brain/tools/impls/propose_write.py` (that is `brain.files.pending.create`, the
   file-write-approval request queue — a different subsystem; flagged by the stage-3 reviewer).
2. **ALLOWED-DIRECT memory writes (the pinned bypass allowlist):** the 4 owner-BYPASS runtime
   writers (`recovery/engine.py` ×2, `body/events.py`, `grief/breadcrumb.py`,
   `kindled_link/relationship.py`) + gate internals (`engines/consolidation.py`,
   `memory/pending.py` route_write's bypass branch) + explicit-user tools
   (`tools/impls/add_memory.py`, `add_journal.py`, `crystallize_soul.py`) + soul promotion
   (`soul/review.py`) + migration tooling (`brain/migrator/*`).

Because the guard matches **all** `.create(` and subtracts only the two *pinned* lists, a NEW
automatic writer using ANY receiver name (`store`, `s`, `mem_store`, …) that direct-creates a
memory is NOT in either list → test FAILS (fails safe on a novel/aliased receiver — the
reviewer's concern). A regression of any of the 4 routed loci back to direct `store.create`
also fails. After this change the 4 routed loci no longer match `\.create\(` at all (they call
`route_write`), so they are absent from the enumerated set.
The pinned lists are keyed by **`(file, exact line-text)`**, NOT `(file, line-number)`, so an
unrelated edit that shifts line numbers inside an allowlisted file does not false-fail the
guard (round-2 reviewer note).
*Oracle:* line-regex enumeration over `brain/**/*.py` vs. the pinned union.
*Shown-able-to-fail:* inline negative sub-checks in the test — (i) assert the enumerator, run
against a synthetic `foo.create(` line, classifies it as un-pinned (would fail); (ii) assert
none of the 4 routed loci files appear in the enumerated `.create(` set post-change.

## Advisory
- **A1 (advisory):** `GATE_BYPASS_TYPES` remains `{journal_entry, initiate_outbound}`
  unchanged (documents that the grief/kindled bypass is call-site, not type-policy — matches
  the pinned owner-scope comment at `pending.py:46-48`).
- **A2 (advisory — named blast radius, CH8; scope corrected round 2):** `_wire_memory`
  (`files/commit.py`) writes fixed low-cardinality content — exactly `"you let me write to
  {path}"` / `"you declined my write to {path}"`, no timestamp or other differentiator. Under
  gating, Pass-1 exact-dup does TWO checks: within-batch (`consolidation.py:172-175`) AND
  against **all existing active `memories.db` rows** via `_has_exact_existing` →
  `store.search_text` with **no time bound** (`consolidation.py:176-179`, `store.py` search).
  Because `_normalize` only whitespace-collapses/casefolds, this means: **after the first
  `file_write` memory for a given (path, outcome) is promoted, every later identical one — at
  any future idle tick, any session — is dropped permanently from the recall channel.** The
  full history is retained in `audit.jsonl` (a separate non-recall log); recall keeps one
  memory per (path, outcome). This is the consolidation gate's designed exact-dup behavior
  applied to a type the owner explicitly ordered gated; file_write's low-cardinality content
  (not the gate mechanism) is what makes the collision rate high. Judgment: **arguably
  desirable** (one "you let me write to X" in recall instead of N identical rows), accepted as
  advisory — but the true permanent/cross-tick scope is **surfaced to the owner in the
  completion report** so the GATE-vs-BYPASS ruling for `file_write` can be revisited if the
  owner wants every occurrence retained in recall. Observed by a documenting test (no gating
  assertion — the drop is intended gate behavior).
- **A3 (advisory — named blast radius, CH8):** gating `self_model_reconcile` delays the
  emotional-delta memory's visibility from "immediately in `memories.db`" to "next idle tick,
  and only if promoted (not exact-dup-dropped / merged)." Verified against source
  (`reconcile.py:177-186`): the gap's `status="acknowledged"` + channel cooldown are set based
  on `gap is not None`, **not** on the memory write — so the acknowledge/cooldown logic is
  UNCHANGED by this routing and never depended on the memory being in the DB. The only change
  is the supplementary emotion memory's visibility latency, which is inherent to gating ANY
  type (the owner's explicit ruling). Named here so the blast radius is measured, not blocking;
  surfaced to the owner in the completion report.

## Non-applicable lenses (explicitly)
- **Position-sensitivity (CP6/ST1.5d):** N/A — this is ordinary name-bound code
  (swap `store.create(x)` → `route_write(store, x, …)`), not a position-sensitive assembly.
- **Concurrency (CP7/ST1.5e):** N/A — no new shared-state accessor or read-modify-write
  window is introduced. `route_write`→`enqueue` uses the existing `file_lock` on the queue;
  this change only adds *callers* of an already-guarded path, it does not alter the guard or
  its scope. (Stated so the stage-3 reviewer can confirm rather than assume.)

# P0 image-tool-route — Acceptance Criteria

Each criterion is labeled **[GATING]** or **[ADVISORY]** and names how it is verified. Per ST1.5f, every
oracle must be demonstrated able to fail on a known-violating input before its pass counts. This change
touches a **position-sensitive assembly** (the prompt system-message / `volatile_suffix` split), so
behavior-preservation criteria (C5 volatile-survives-post-file-turn, C9 text-only byte-preserving, C14
path-line-does-not-perturb-salience/volatile) are included and must be verified by execution (ST1.5d). No new
shared-state accessor is introduced (the content-addressable `/upload` store is idempotent, tmp-then-rename),
so ST1.5e does not fire.

## The capability — a viewable image via the real MCP server

- **C1 [GATING] — an image `read_file` returns a viewable image through `brain.mcp_server`.** Driving the
  *real* `brain.mcp_server` under the companion's real posture (`claude -p --output-format json
  --mcp-config <real server> --allowedTools mcp__brain-tools__read_file --disallowedTools <the 11
  builtins>`), the model, asked to `read_file` an image rendering a fresh random secret token and report the
  characters, returns the **exact** token on **≥3 runs with a fresh secret each time**, against the
  companion's **pinned chat model**. *Oracle:* string-equality of model output vs. the harness-known secret.
  *Shown-able-to-fail:* the negative control (C2) is the same harness returning a text-only result and must
  FAIL to produce the token. (Extends the single-run spike to the spec's ≥3 bar on the real server/model.)
- **C2 [GATING] — negative control proves the image is the source.** Same harness, `read_file` on the same
  image but with the image-content path disabled so it returns TEXT only → the model **cannot** produce the
  secret (returns "NO IMAGE" / wrong token). Proves C1's pass comes from the rendered image, not prompt
  leakage. *Oracle:* secret token absent from output. *Shown-able-to-fail:* it fires (secret absent) here
  and must NOT fire under C1's positive path.
- **C3 [GATING] — text files still return text.** `read_file` on a normal UTF-8 text file returns its text
  content (a `TextContent` payload with the file's bytes), unchanged from today. *Oracle:* automated —
  returned content contains a known unique line from the fixture file. *Shown-able-to-fail:* run against a
  non-existent path → must return an error, not content.
- **C4 [GATING] — MCP-only posture preserved.** Built-in `Read` remains in `_BUILTIN_TOOLS_DISALLOWED` and
  the emitted `--disallowedTools` set; no built-in file tool is enabled by this change. *Oracle:* automated
  assertion over `_BUILTIN_TOOLS_DISALLOWED` and `_apply_lean_flags` output. *Shown-able-to-fail:* the
  assertion fails if `Read` is removed from the tuple (verify by a temporary local mutation).
- **C12 [GATING] — a real-photo-sized image is returned, not refused (fixes red-team F-1/G1).** `read_file`
  on an image whose size is **between the 256KB text cap and `files.image_max_bytes`** returns an image
  result (a structured image payload / `ImageContent`), NOT `"file too large"`. This guards the cap-ordering
  bug: if the image branch sits after the text-cap check, every real photo (>256KB) is silently refused.
  *Oracle:* automated — `read_file` on a >256KB image fixture returns the `image` key, not an error.
  *Shown-able-to-fail — REQUIRED:* (a) an image **larger** than `files.image_max_bytes` IS refused (own
  "image too large" error), proving the image cap is live; and (b) the identical >256KB image, run against
  code where the image branch is placed *after* the text cap (or against pre-change), returns
  `"file too large"` — reproducing the F-1 regression the ordering exists to kill. *Precondition:* this
  criterion presupposes `files.image_max_bytes > 256KB` (else its discriminating range is empty and the
  test is vacuous). **Per owner ruling, `files.image_max_bytes` is set ≥ the `/upload` cap (20 MB,
  `server.py:2145`)**, which both satisfies the >256KB precondition and removes the upload-succeeds-but-
  read-refuses dead zone (red-team lap-2 minor, ratified).
- **C13 [GATING] — she sees an organically-shared image without being told to read it (the actual #48
  requirement; fixes red-team F-3/F-5/G2).** Driving the real `brain.mcp_server` under the real posture and
  pinned model, a **natural** turn — an image rendering a fresh random secret is shared and the user asks
  about it in ordinary language with **no** "call read_file"/"use the tool" instruction — results in the
  model reporting the **exact** secret. This is the behavior the owner's hard requirement protects ("whatever
  replaces `_chat_with_images` must still let her *see* images", spec Prior-art). C1 proves the *instructed*
  read works; C13 proves the *organic* path — the scenario #48 was about — works. *Oracle:* string-equality
  of model output vs. the harness-known secret, over **≥3 natural-prompt runs with a fresh secret each**.
  *Shown-able-to-fail:* the text-only / no-image control (same natural prompt, no image) → secret absent.
  *If C13 fails, that is a **blocker** routing to owner* (see plan thresholds / open axis 4): opt-in-via-tool
  did not deliver automatic-equivalent seeing, and the design must proactively emit the read — not a silent
  runner fix.

## The bug fix — volatile context survives an earlier image (position-sensitive behavior)

- **C5 [GATING] — volatile context survives a text turn that follows a file-send turn (behavior-preservation
  / the bug fix).** In a session where turn *k* shared a file and turn *k+1* is a text-only turn, turn
  *k+1*'s assembled prompt **contains its `volatile_suffix`** (ambient/volatile context). *Oracle:* execute
  the two-turn sequence through the engine and assert the volatile context is present in the k+1 assembly.
  *Shown-able-to-fail — REQUIRED, this is the regression the change exists to kill:* the identical oracle,
  run against the **pre-change** code (`git stash`/base commit), MUST show the volatile context **absent**
  on turn k+1 (reproducing the volatile-drop bug). A criterion that passes on both pre- and post-change code
  proves nothing (per ST1.5d / spike-representativeness).
- **C14 [GATING] — the surfaced path line does not perturb salience/volatile (fixes red-team F-4/G4).** On
  a file-send turn, the volatile/salience-derived content of the assembled prompt is **equivalent to the
  same user text without a shared file** — i.e. the injected `[the user shared a file: <path>]` line is NOT
  fed into `assess_salience` / `build_volatile_context` (it lands only on the outgoing user message). This is
  a position-sensitivity guard (C5 only checks a suffix is *present*, not that its *content* is uncontaminated).
  *Oracle:* assemble a file-send turn and the same typed text without a file; assert the salience flags and
  volatile-seed content match. *Shown-able-to-fail:* prepend the path line into the salience/volatile input
  and the assertion fails (the contaminated build differs).
- **C6 [GATING] — no image/text builder fork remains.** After the change there is no code path where the
  engine's per-turn image check and the provider's replayed-history image check can disagree: `_chat_with_images`,
  the `has_images` branch, `_message_has_image`, and the engine `image_shas` builder-fork are gone. *Oracle:*
  `git grep` for the removed symbols returns nothing in non-test source; a single assembly path is exercised
  for both a file-send turn and a text turn. *Shown-able-to-fail:* the grep matches on the pre-change tree.

## The file-send flow works end to end

- **C7 [GATING] — a shared file's path reaches the model and `read_file` is available that turn.** On a
  turn where a file was shared, (a) the file's path appears in the turn's assembled user text, and (b)
  `read_file` is in the recruited/allowed tool set **regardless of salience score**. *Oracle:* automated —
  assert the path substring is in the assembled turn and `read_file ∈ select_tools(...)` output for a
  file-send turn. *Shown-able-to-fail:* on a text-only turn with low salience and no shared file,
  `read_file` is NOT force-included (guards against always-on over-recruitment); and the path assertion
  fails when no file is shared.
- **C8a [GATING] — frontend image send-path change (IN SCOPE).** `ChatPanel.tsx` sends a shared image so
  its path is surfaced on the normal turn (no `image_shas` transport payload). *Oracle:* the component test
  asserting the send path posts the normal message (with the resolved path) and does NOT set `image_shas`.
  *Shown-able-to-fail:* the old `image_shas`-setting path fails the assertion.
- **C8b [GATING — #43 in scope, option A per owner ruling] — "send file" relabel + non-image types.**
  `ChatPanel.tsx` exposes a "send file" affordance whose accepted-types set includes ≥1 non-image type,
  backed by the widened `/upload`. *Oracle:* component test asserting the "send file" label + a non-image
  type is accepted and staged. *Shown-able-to-fail:* asserting the old image-only accepted-set fails.
- **C16 [GATING — the #43 end-to-end path, option A per owner ruling] — a shared non-image file is stored
  and readable.** End to end: a non-image file (a UTF-8 text fixture with a known unique line) POSTed to the
  **widened `/upload`** is stored on disk, its path is surfaced on the turn, and `read_file <path>` returns
  the file's text content (the known line). This is the criterion the owner named ("send a non-image file →
  stored → readable"). *Oracle:* automated — (a) `/upload` accepts the text file and returns a resolvable
  ref/path (not 415/422); (b) `read_file` on the stored path returns the known line. *Shown-able-to-fail:*
  run against pre-change `/upload` (image-only) → the text upload is rejected (415/422), so the chain never
  starts — reproducing the #43 defect the widening closes. (PDF/other-binary that is not UTF-8 decodable is
  stored and its path surfaced, but `read_file` returns the existing "binary file — not shown" note; #43's
  storage/hand-off is closed for all types, text is fully readable, non-text-binary readability is out of
  scope for this PR — noted, not claimed. **PDF-text-readability specifically is escalated to the owner at
  the post-build gate** — the owner's ruling named PDF as readable, but PDF-text-extraction needs a further
  step/dependency; this is flagged for the owner, not resolved by the runner (final-red-team Finding 1).)
- **C17 [GATING — security, the new file store] — a shared file cannot escape the store directory.** The
  on-disk path for a `save_file_bytes` upload is derived **only** from the validated 64-hex sha (no
  client-supplied filename/extension is ever a path component), so a crafted upload filename (e.g. containing
  `/` or `..`) cannot write outside `<persona_dir>/files/`. *Oracle:* automated — upload a file whose declared
  filename is a traversal payload (`../../etc/x`, `a/b`), assert the stored path resolves under
  `<persona_dir>/files/` and no payload dirs were created. *Shown-able-to-fail:* a store that interpolates the
  filename into the path writes outside the dir and the assertion fires. (Guards final-red-team Finding 2; the
  codebase's threat model treats a compromised local client as in-scope, `server.py:2181-2184`.)

## No collateral regression

- **C9 [GATING] — text-only chat is behavior-preserving on the caching assembly.** For a text-only turn,
  the static-system-message + `volatile_suffix` split (Option A/A+) is unchanged: the static system message
  is byte-identical to pre-change and the volatile suffix still lands in the stdin tail. *Oracle:* execute a
  text-only turn pre- and post-change and diff the assembled system message + suffix placement.
  *Shown-able-to-fail:* the diff is non-empty if the static/volatile split is altered.
- **C10 [GATING] — local CI green.** `uv run ruff check .` clean and `uv run pytest -m "not live and not
  requires_claude_cli and not integration"` passes (py3.12), plus the `app/src` frontend test suite for the
  touched component. *Oracle:* exit codes. *Shown-able-to-fail:* a deliberately broken test fails the run.
- **C11 [ADVISORY] — cost/cache regression signals.** The config's standing regression metrics
  (`cost_per_chat_call_usd`, `num_turns_per_chat_call`, `cache_creation_per_chat_call`, `cache_read_ratio`)
  show no material adverse move on a representative set of turns. *Advisory reason:* per the project config,
  no comparable replay workload exists yet, so all regression metrics are advisory-only (H8); a file-send
  turn legitimately does more work (an extra tool call) so an isolated delta is expected and non-blocking.

- **C15 [ADVISORY] — image reads stay auditable without base64 bloat (red-team G5).** The `file_access` /
  MCP audit line for an image `read_file` records a compact summary (e.g. `image/png <N>B`), NOT the base64
  payload. *Oracle:* the audit row for an image read contains no long base64 blob. *Advisory reason:*
  log-hygiene, not load-bearing behavior; folded here so the build remembers it.

## Notes for stage 8

- C1/C2/C13 reuse and extend the spike harness (`~/p0-image-spike/`) but must point at the **real**
  `brain.mcp_server` and the **pinned** chat model resolved from the persona config (not a hardcoded alias,
  not the throwaway FastMCP server / `sonnet`).
- **C13 is the criterion that encodes the owner's end-to-end #48 requirement** (organic seeing), distinct
  from C1's instructed read. Its failure is a blocker routing to the owner (design must proactively emit the
  read), never a silent runner workaround.
- **C12** guards the F-1 cap-ordering bug: without the >256KB shown-able-to-fail run against mis-ordered code
  it proves nothing, since C1's secret-token image is tiny.
- C5, C9, C12's "shown-able-to-fail" runs against the pre-change / mis-ordered base are mandatory, not
  optional — they are what make these gating criteria discriminating rather than tautological.

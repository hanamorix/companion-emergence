# 1.5 — Acceptance criteria (separate-queue architecture)

Each criterion is **automated** (true/false or numeric from a test) unless marked a rubric. Default
**gating**; advisory only with a stated reason. Every oracle must be **shown able to fail** (ST1.5f):
run each test against the pre-change / known-violating state and confirm it flags the violation,
else `verified = no` at stage 8. Fixture naming: synthetic user = **Bob**, persona = **Canary**,
model = **Claude**. Phoebe is never a fixture.

**Magnitude note (C6–C8):** these verify the mechanism does the *structurally correct* thing **given
a decision/threshold**, using the conservative default + (for Pass 2) an injected stub classifier.
They do not assert aggressiveness of dedup/merge (deferred L-B knob).

---

### C1 — Automatic writers ENQUEUE; candidate is not a `memories.db` row (gating)
An automatic firehose write lands in the **pending queue**, not in `memories.db`.
- **Check:** for a representative automatic writer (e.g. `monologue/trace.py`, `chat/extractor.py`,
  `engines/dream.py`), invoke it and assert (a) the entry is in `PendingQueue` and (b) **no
  `memories.db` row exists** for it (`store.search_text`/`list_by_type` returns nothing).
- **Fail-demo:** pre-change the writer creates a `memories.db` row → (b) fails.

### C2 — Candidates never reach recall (gating)
Because candidates are not in `memories.db`, the **unchanged** recall channel cannot surface them.
- **Check:** enqueue a candidate whose content matches a query token; assert `_build_recall_block`
  (both branches) and the `search_memories` tool return **nothing** for it. Then `store.create` a
  genuine memory with matching content and assert it **does** appear (recall still works).
- **Fail-demo:** if a writer wrongly wrote the candidate to `memories.db`, recall would surface it.

### C3 — Interior-continuity reads recent traces from the QUEUE, not starved (gating; ST1.5d)
Both `monologue/ambient.py` (`build_interior_continuity_block`) **and** `monologue/recall.py`
(`recall_monologues`) surface recent `monologue_trace` from the pending queue, so both still fire.
- **Check (by execution):** enqueue N `monologue_trace` candidates; (a) call
  `build_interior_continuity_block` → assert the recent traces are present; (b) call the
  `recall.py` path → assert it surfaces matching queued traces. `_AMBIENT_LIMIT` stays 5 and the
  block's rendering semantics are unchanged (owner directive 3) — assert the limit and header/footer
  are untouched.
- **Fail-demo:** the pre-migration code reads `store.list_by_type` from `memories.db` (now empty of
  traces) → empty block. Confirm the test fails against the un-migrated read.

### C4 — REJECT discards from the queue with ZERO `memories.db` side effects (gating)
A gate rejection (exact-dup, low-salience, Pass-2 `duplicate`) removes the entry from the queue and
touches nothing in `memories.db`: no row, no graveyard, no grief, no hebbian edge.
- **Check:** drive the gate (stub-driven where needed) over candidates covering reject verdicts, with
  `store.create`, `graveyard.append`, `grief.handle_drop`, and `hebbian` **spied** → assert none is
  called for a rejected candidate, the queue no longer contains it, and `memories.db` count is
  unchanged.
- **Fail-demo:** any implementation that materializes a rejected candidate in `memories.db` (or
  files a graveyard/grief entry) → spy assertion fires.

### C5 — PROMOTE writes a genuine `memories.db` row, faithfully (gating)
A `distinct`/`new` verdict promotes the candidate via `store.create(Memory.from_dict(entry))`, it
then appears in recall, and the promoted row **preserves the candidate's fields** through the
`to_dict → from_dict → create` round-trip.
- **Check:** stub `new` → assert a `memories.db` row exists and `_build_recall_block` surfaces it;
  **plus** a round-trip assertion that a candidate with non-trivial `emotions`, `importance`, `tags`,
  and `metadata` promotes with those preserved (round-4: `to_dict` drops `peak_emotion_intensity`/
  `state`/`content_snapshot`/`recall_count`, but `create` recomputes peak from `emotions` and the
  rest take new-row defaults — assert emotions/importance/tags/metadata survive).
- **Fail-demo:** a no-op promote leaves recall empty; a lossy serialization drops emotions → the
  round-trip assertion fires.

### C6 — Pass 1 discards exact repeats only, never non-identical (gating)
Exact repeats (after whitespace+case normalization, within the batch or vs an existing `memories.db`
memory) are discarded from the queue; a non-identical near pair is never discarded by Pass 1.
- **Check:** unit — (a) identical pair → one discarded, the other survives to promote/Pass-2;
  (b) "dog ate cat food" / "dog ate the cat as food" → **both** survive Pass 1.
- **Fail-demo:** a similarity-threshold discard kills one of (b) → assertion fires.

### C7 — MERGE archives a lossless pre-image (plain file) + surgical edit + discards candidate (gating)
Stub `merge` → archive the existing memory's pre-image to the **plain append-only archive file**
(NOT the grief graveyard) **before** editing, surgically edit the existing `memories.db` memory to
fold in the new fact, and discard the candidate from the queue.
- **Check:** integration — assert (a) a plain-archive record for the pre-image written **before** the
  mutation, (b) the edited `memories.db` memory contains both facts, (c) **no** grief-graveyard entry,
  (d) the candidate is gone from the queue and was **not** also promoted (no duplicate row).
- **Fail-demo:** overwrite-without-archive → (a) fires; graveyard use → (c) fires.

### C8 — Corrections & continuations promote + weight-5 edge, even over a prior edge (gating)
Stub `correction`/`continuation` → the candidate is **promoted** (its own `memories.db` row, not
merged away) and a hebbian edge of weight **5.0** links it to the referent, including when a weaker
edge already exists.
- **Check:** integration — assert the promoted row exists and `hebbian` reports edge weight `== 5.0`
  to the referent; plus a pre-existing-edge case (seed ~0.5 first → raised to 5.0).
- **Fail-demo:** merge-instead-of-link fails the promotion assertion; bare-`ensure_edge` fails the
  pre-existing-edge case.

### C9 — Gate runs first on the idle tick (gating)
The consolidation step executes before reflex/dream/research in `heartbeat.run_tick`.
- **Check:** spy ordering — consolidation call ordinal precedes `_try_fire_reflex`.
- **Fail-demo:** ordering it after reflex → assertion fires.

### C10 — No lost candidate under enqueue-during-drain interleaving (gating; ST1.5e — the QUEUE)
The pending queue is shared mutable state (many firehose appenders + the gate drainer). A candidate
enqueued during the drain's read-modify-truncate window is not lost.
- **Check:** enqueue C concurrently with a `drain()`; assert C **serializes and survives** — it is
  either in the drained batch or still in the queue afterward, never lost. (Because `file_lock`
  serializes append vs read+truncate, a real "between read and truncate" interleave is *impossible*
  in the guarded path — so the pass-side assertion is "no candidate is lost across a concurrent
  enqueue/drain," not a literal mid-window injection.)
- **Fail-demo (must fail against the unguarded variant):** a drain that reads-then-truncates
  **without** holding `file_lock` over the window drops C injected between the read and truncate (the
  exact soul-candidate P2-2 defect) → assertion fires. Test passes with the lock, fails without.

### C11 — No double-fold under overlapping gate runs (gating; ST1.5e — `memories.db` merge target)
Two overlapping `run_tick` gate runs (background vs close vs CLI) must not double-fold a merge target.
- **Check (injected):** stub a `merge` on candidate X→target Y; invoke a second `run_consolidation`
  while the first holds the non-blocking gate lock → assert the second returns `skipped` and Y was
  folded exactly once (one pre-image archive record).
- **Fail-demo:** without the lock both fold X→Y (two archive records) → assertion fires.

### C12 — Deliberate / import / restore writes go straight to `memories.db` (gating)
Explicit `add_memory`, `add_journal`, migrator import, recovery restore land as genuine `memories.db`
rows (not enqueued).
- **Check:** unit per path — invoke each and assert a `memories.db` row exists (and nothing was
  enqueued).
- **Fail-demo:** a path wrongly enqueuing → assertion fires.

### C13 — Recall / forgetting / cache-prefix code is UNTOUCHED (gating)
This architecture needs no recall filter, so the recall and forgetting code and the cache-stable
prefix must be unchanged.
- **Check:** `git diff` touches **none** of `chat/prompt.py` `_build_recall_block`,
  `forgetting/recall.py`, `tools/impls/search_memories.py`, `forgetting/__init__.py`,
  `chat/prompt.py` `build_static_system_message`, or `chat/engine.py` history replay; existing
  recall/prompt-cache tests still pass.
- **Fail-demo:** an accidental edit to any → diff assertion fires.

### C14 — TEMP marker + removal dependency filed (gating)
Gate code carries `TEMP (Root 2 stopgap — remove when Phase 2 relevance overhaul lands)` and the
removal is recorded as a Phase-2 dependency (not a repo coordination file).
- **Check:** grep for the marker; confirm the dependency record.

### C17a — Initiate outbound dedup does not double-send (gating; testable NOW)
The outbound-repeat guard must still work under the queue architecture. Default resolution:
`initiate_outbound` is **excluded** from `GATED_TYPES` (writes direct), so `initiate/memory.py:105`
sees every outbound.
- **Check:** exercise the send path so an outbound is recorded, then attempt a duplicate → assert it
  is suppressed. With the default (direct), this passes against `memories.db`; if the owner instead
  gates `initiate_outbound`, the test requires initiate's dedup to also read the queue and still
  suppress. Gated and testable now — **not** deferred behind the product decision (round-4: the
  mechanism is a build choice, not a product choice).
- **Fail-demo:** gating `initiate_outbound` **without** teaching the dedup to read the queue → the
  duplicate is sent → assertion fires.

### C17b — Bridge feed reflects the owner's ruled behavior — RESOLVED (advisory)
**Owner ruled (R3): consolidated-only is accepted; `feed.py` keeps reading `memories.db` → promoted
items only; NO code change.** So there is nothing to build or gate here — the feed behavior follows
automatically from candidates not being in `memories.db`.
- **Advisory check:** confirm `feed.py` is untouched by the diff and the dream/research feeds return
  promoted items (a natural consequence, verified incidentally). No separate gating test needed.

### C18 — Legitimate dream / research / trace content survives the gate (gating; owner directive 4 / R3)
Salience-drop is confined to `SALIENCE_ELIGIBLE_TYPES` (monologue-episode types); a flat-emotion
`dream` (importance≈0), a `research` memory, and a `monologue_trace` (0.3) are **not** wholesale
salience-dropped, **even with a `SALIENCE_FLOOR` set** — they proceed through dedup and (barring a
true duplicate) promote / remain.
- **Check:** set a `SALIENCE_FLOOR` above 0.3 (e.g. 1.0); enqueue a flat-emotion dream (no emotions →
  importance 0.0), a research memory (low emotion-derived importance), and a `monologue_trace`
  (0.3), each with distinct non-duplicate content; run the gate; assert **none** is salience-dropped
  (the dream/research promote to `memories.db`; the trace remains available via the queue). Then a
  low-salience `monologue`-EPISODE row (importance below floor) **is** dropped — proving the scope is
  live, not a no-op.
- **Fail-demo (must fail against a single-floor variant):** a naive salience-drop applying the floor
  to all gated types discards the flat dream + trace → assertion fires. The test passes against the
  type-scoped implementation and fails against the blanket-floor one.

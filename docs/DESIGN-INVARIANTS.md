# companion-emergence: design invariants

Status: reviewed 2026-09-15 by ThinkerOfThoughts. I4 amended 2026-09-28 and 2026-09-29. I8 amended 2026-09-29 and 2026-10-22; the last clause of I8 was corrected on 2026-10-23 to match ThinkerOfThoughts's wording ("purely a crash recovery measure").

These are standing architectural rules set by ThinkerOfThoughts. Every plan, spec, review and drift check for a change is checked against them, row by row. A line is added only with a recorded decision by ThinkerOfThoughts and its date; a line is removed only by ThinkerOfThoughts. The invariants were seeded on 2026-09-15 from recorded rulings by ThinkerOfThoughts and reviewed the same day. The emotion rework spec (`docs/source-spec/2026-10-28-emotion-rework-owner-half-design.md`, section 5) checks I1 to I14 against the rework.

| # | Invariant (one checkable sentence) | Why (ThinkerOfThoughts's reasoning, date, issues) |
|---|---|---|
| I1 | There is one memories database; hebbian associations live in `memories.db`, not a separate file. | Keeping them in a separate file is fragile: on one occasion a persona's hebbian links had to be reconstructed after the files were copied from one machine to another. 2026-09-15; #128; the memory-database restructuring (its Stage 1). |
| I2 | A per-memory attribute (embedding, cluster tag, the memory's own emotion tag) is stored on the memory row, or in a memories-side table keyed by memory id; never in a content-addressed side file. Emotion SIGNAL entries (standalone rows holding only the emotional state at time of entry, with no memory content) are not per-memory attributes; they are a separate thing, see I8. | Per-memory embeddings were meant to be an additional column in the memory database. 2026-09-13; #259. |
| I3 | Behaviour thresholds (floors, gaps, cutoffs) are derived or self-calibrating; a hardcoded empirical constant is a tracked defect, never a finished answer. | Magic numbers in code are very rarely the right answer, and a threshold should recalibrate itself to the database as it currently is. 2026-09-09 and 2026-09-12; #250. |
| I4 | On automatic (passive, per-turn) recall, semantic retrieval runs first and ranks first; the lexical/importance/hebbian/recency results are always merged in below the semantic ones, and when the same memory is found by both, the semantic result is the one kept (dedup favors semantic). Exception: monologue-family memories that were not reranked (gated only by the cosine pass mark) rank below keyword genuine hits. On a kindled-initiated search, semantic is the default mode and the kindled can switch it to lexical. | Semantic search is the primary mechanism and lexical is the fallback; it runs first on automatic recall and is the default for kindled-initiated searches, which can switch it to lexical. 2026-09-09, 2026-09-15. Amended 2026-09-28 (name-recall fix): lexical results are always merged in, and deduplication favors the semantic result. Amended 2026-09-29: non-reranked monologue results rank below keyword genuine hits (only the tail drops). |
| I5 | A memory opened in full gets the full recall bump and is enqueued for reappraisal, regardless of which path surfaced it. | If a memory surfaces it gets the full +1 to its recall score however it was surfaced, and an opened memory goes back into the reappraisal queue. 2026-09-10. |
| I6 | Bulk background work (backfills, sweeps) stays off the message hot path; a single bounded per-turn step is acceptable; the lag rule targets floods, not one call. | An extra tens of milliseconds on a message is a non-issue; the lag to avoid is a flood of hundreds of queries per minute. 2026-09-09. |
| I7 | Constants and prompt strings live outside the mechanism code: user-facing knobs in `tunables.py`, dev-facing constants and prompt strings in their own files, model ids in `model_tier.py`. | Code is where mechanisms live; constants belong outside it. The model used is specified in `model_tier.py`, and the same goes for any future mini-models. 2026-08-12, 2026-09-09; #129. |
| I8 | Journal entries move out of `memories.db` into their own store. Emotion signal entries do not get a store of their own: there is no separate emotions database or emotion-only entries; a kindled's felt state (short- and long-term moving averages) is computed from the emotions of surfaced memories plus emotional changes from interactions/events (amended 2026-09-29). Exception (amended 2026-10-22): a crash-recovery record of emotion changes may exist only where it is actually needed to recover from a crash; it has no tie to memory or database entries, is never read in normal running, and only crash recovery (a rebuild, or catching up from a backup copy) reads it. | The emotional signal entries were to move to an emotions database, but the detail of that store was pending the untangling of the emotion system (2026-09-10, 2026-09-15; #222, #224, #240). Amended 2026-09-29: once it was clear what the entries actually did, no separate emotions database or emotion-only entries need exist. Amended 2026-10-22: a log that is purely a crash-recovery measure, tied to no memory or database entries, is allowed, but only where it cannot be avoided; a recovery log that is not needed to recover from a crash is not wanted. |
| I9 | Any storage change keeps the legacy import path working and ships a run-once, fail-safe migration that verifies the new stores before removing anything. | Storage changes must not break backwards compatibility, and need a run-once check that the updated memory, emotion and journal stores are intact and correct before anything is removed. 2026-09-10. |
| I10 | Persona-facing and prompt strings carry no LLM tells (no em-dashes) and say "kindled", not "companion"; their wording is ThinkerOfThoughts's byte-exact call, finalized at the end of a build. | Standing rules by ThinkerOfThoughts: no LLM tells on the persona's prompt surface, "kindled" is the default term, and string wording is deferred to the end of a build. |
| I11 | A live persona is never driven as a test fixture; tests use the synthetic user and persona named in the harness notes. | Standing rule by ThinkerOfThoughts. |
| I12 | A feature or fix never increases the technical skill required of the user: an optional or heavy component is provisioned/enabled automatically on capability detection, never by a user-run install or a manual pip/python step. Each change should ideally lower the bar, toward a non-technical user eventually running it without issue. | Requiring a user to handle Python directly is the wrong way to do this; a feature or fix should at minimum not make things harder and should ideally make them easier. 2026-09-24; the optional LoRA dependencies work. |
| I13 | This is a cross-platform project: every feature, installer, and deployment/provisioning mechanism must work on macOS, Windows, and Linux. Linux/.deb/systemd is one deployment path, not the primary or only one (the user base skews Mac + Windows; Linux is the minority). | Users are on macOS, on Windows and, as a minority, on Linux. 2026-09-24. |
| I14 | Support machinery never outgrows the thing it serves: when a test harness, or a self-calibration (measured costs, fitted bounds), costs more to build than the feature it tests or calibrates, the work stops and ThinkerOfThoughts chooses keep going, simplify, or freeze. | If making a test for a thing takes longer than making the thing, or the self-calibration for a thing takes longer than the thing being calibrated, something is wrong. 2026-10-10; #321 grew from 55 approved decisions to 247, mostly timing and memory self-calibration plus a timing harness rebuilt five times. |

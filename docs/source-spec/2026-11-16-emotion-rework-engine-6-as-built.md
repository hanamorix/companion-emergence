# Emotion rework, Engine 6: the switch-over, as built

This records what PR #633 built (issue #584). It supersedes the Engine 6 parts of the rework design doc on the plan branch (sections 2.12, 3.2, 3.3 and the Engine 6 rows of section 6) where they differ. That doc still describes a switch file, a `user_version` marker of 1 only and a row-count rollback, all replaced by later owner rulings. The timing figures below were measured on 2026-11-11 at head 883915e7 and not re-measured since; the per-group test table is from the same day. The whole-branch test count, the full local suite and the CI figures were re-run on 2026-11-17 at head 8d5356be, and the rest was refreshed to that head. Timings are from the desktop VM with AVX2 masked.

## Why

This is the point where the emotion engine becomes the source of truth. Until now it ran in shadow beside the old code. This change makes it live and removes the old decay pass in the same change, because the switch-over, the fade on read and the end of the old pass have to land together, or memories would fade twice or not at all.

## What changed, in full

1. **Start-up.** `ensure_engine_ready(persona_dir)` runs before any reader, in the rebuild process (`nell supervisor rebuild`, S107): the start of the bridge and the six commands (`_chat_direct_mode`, `_heartbeat_handler`, `_dream_handler`, `_reflex_handler`, `_research_handler`, `_soul_review_handler`) run that process first and wait for it. The bridge's `lifespan` no longer calls it, and each command handler, right after its own vocabulary load, runs the rebuild step instead (`_engine_ready_or_refuse`: register the command, then `daemon.run_rebuild_step`). A persona is "switched over" when its emotion state file (`state/emotion_state.json`) holds a `switch_over_at` time. There is no separate switch file. If the state holds it, `ensure` returns at once with no transaction and no lock. Otherwise it runs the one-off x10 fix (below), takes the engine lock once, and runs the first rebuild: it folds the stored values of every counted memory created or accessed in the last 30 days, replays the change log, infers past active days, sets the persona's start date from its oldest memory of any type, checks the result, empties the engine's queue file (it is emptied, never deleted), and writes the state once, verified; that one write records `switch_over_at`, so it is the switch-over's last step. A failure stops start-up with a named `EngineStartupError`, and the next start runs the step again. The exception is an engine lock held by another process (usually a rebuild a dropped start left running): the rebuild process waits for it (the owner's ruling: the start-up waits until the rebuild is finished), trying again in steps of the lock wait (5 s) with a throttled log line each, with no stop check and no limit. When the lock comes the re-check under it decides: the other process finished the switch-over (nothing to run) or failed (this start runs the rebuild). A command whose rebuild step finds a start or another rebuild holding the start lock is refused at once (exit code 2, one plain line saying to try again when it has finished; `nell chat` stops on it like the other five), and one that cannot end another running command gets exit code 1. Only the supervisor's recovery job (`recovery_rebuild`) keeps the one 5 s wait and the failure. While the x10 fix and the first rebuild run, each writes a small progress record, `engine_progress.json` in the persona directory (phase "rescaling" with no count, or "rebuilding" with the memories done of the total, rewritten on each whole percent, at most 102 writes; removed when the step ends, success or failure; never written over another live process's record; the first rebuild, and the rebuild of a roll-forward, also write the "rebuilding" record with no count at the top of every pass of their lock wait, before the lock is tried, so a start that waits for the engine lock shows it, and write it again at the next wait step if it was removed or refused meanwhile); `nell supervisor status --json` returns it as `engine_progress` while its writer is alive and `null` otherwise (the start waits that pause on it and the screens that show it are part of the same change; the record is written by the rebuild process, see "The start-up rebuild process"). A state that exists but cannot be read (no copy of it, main or backup, can be parsed) is treated as "not switched over" by readers and writers, and the start-up decides from the database's own record of the x10 fix (below): the x10 steps read their progress number and skip what is done, then the first-mode rebuild writes a fresh readable state with `switch_over_at` set to now (first mode, because a recovery rebuild copies the time from a loaded state and there is none to load). The rebuild's one state write simply replaces the unreadable state (the owner's ruling): its normal backup rotation moves the unreadable main file into `.bak1`, the old copies age out over the next saves, and nothing moves, keeps or deletes them. If that write fails with an I/O error (a directory or an unreadable file at the state path, or a directory at `.bak3`, which the rotation unlinks) on a state the start-up found unreadable, that start skips the switch-over, logs one warning naming the file and the error, and start-up goes on; the persona stays not switched over and the next start tries again (an I/O fault is a skip and a retry, never a stop at every start). Every other rebuild write failure still stops start-up. While the state is unreadable the drain and the direct apply skip their pass and keep the queue (they never start from an empty state, and the same holds when the catch-up of a backup state fails for a persona not seen switched over). If `memories.db` fails its integrity check too, that start is skipped with a logged reason and retried at the next start; a persona that switched while `memories.db` was absent and later loses its whole state file is rebuilt as never switched (an accepted edge).
2. **Dry runs.** A `--dry-run` of a handler on a persona that is not switched over does not call `ensure`, runs no reader, writes nothing, prints a plain message on stderr and exits with code 2. A persona that is already switched over goes on as before.
3. **Recovery.** A new gated background job, `emotion_recovery_rebuild` (first in the job order, no interval, due while the engine reports it needs recovery), rebuilds the state from the database for a switched-over persona whose state is missing or unreadable. It never raises, and logs a failure once per active day.
4. **Live reads.** After the switch-over, `faded_value` fades a stored value on read (from the later of the memory's creation and the switch-over time), working only from the values it is given, so it also serves a row the caller has already deleted. `fold_change` writes one change-log line first. Before the switch-over, and for a persona whose state cannot be read, `faded_value` returns the stored value.
5. **Peer trust.** `engine_files.peer_trust` now calls the peer-trust accessor that is already on main (#685). The engine guards any exception that accessor does not catch with trust 0.0 and a throttled warning, so a hook, a catch-up and the rebuild all fall back to the floor instead of dropping an event (tracked as #705, fixed in #656).
6. **Days since the user last spoke.** `days_since_human` reads the user's last turn from the conversation files through one new function, `last_user_turn_ts` in `brain/ingest/buffer.py` (the later of the active files' newest user turn and the newest archived session's: the archive walk is seeded with the active result; nothing is created). Each conversation file is read from its end backwards and the read stops at its last user row (`iter_jsonl_reversed` in `brain/health/json_io.py`); a bad line is skipped with a warning, so it never hides an earlier user row. The value is that last user row's ts, not the largest ts in the file. It no longer reads memories or the presence file, because a recalled memory's `created_at` can move. `user_pattern` takes its silence from the same function. The two old helpers and a third dead one are deleted.
7. **The old decay pass is removed:** `HeartbeatEngine._apply_emotion_decay` and its resume path, `brain/emotion/decay.py`, the batch budget constant, `DecayCursor` and the state field (an old `decay_cursor` key in `heartbeat_state.json` is ignored on load and dropped on the next save), `memories_decayed` everywhere (the tick result, the `heartbeat_tick` event, the log row, the stored daemon-state summary, the heartbeat prompt segments, two command lines), `MemoryStore.update_emotions_batch` and `list_active_since`, and their tests. The removed names are in the removed-names test.
8. **The x10 fix of small feelings.** Old rows of type `initiate_outbound`, `kindled_peer` and `making` stored their feelings on a 0 to 1 scale; the engine reads 0 to 10. Rows whose strongest value is below 1 are multiplied by 10 (feelings, score and peak, the whole row; a negative feeling or peak is held to 0.0 first, as the owner ruled that negatives are converted to 0, and the score is multiplied as stored), in one transaction inside one new `MemoryStore` method, because the store is the only writer of `memories.db`; the database's own transaction makes it all-or-nothing, so the fix does not read the rows back to compare them (the owner ruled that what another system already recovers is not done again). A row or entry with no feelings is multiplied too, in its peak and score (a decayed row keeps its peak). Waiting `making` candidates in the pending queue (both queue files) get the same multiply, because the consolidation gate would otherwise promote them at the old size. The queue step runs in this order: if neither queue file exists the number below is set to 2 and the step stops, taking no lock; otherwise the queue's lock is taken; the number is read inside the lock and, if it is already 2, the step stops (so a bridge and a command that start together cannot both multiply); both files are read and each file's new content is built in memory (a read fault stops start-up with nothing changed, and the next start tries again); the number is set to 2 (a failure stops start-up with nothing written); each file with at least one multiplied entry is rewritten once with the shared atomic writer (a missing, empty or nothing-selected file is not created or rewritten; a failed write is logged, saying that file's entries stay at the old scale and will not be retried, and start-up goes on); the lock is released. Nothing is marked on any row or entry, and no temporary copy is made. The progress of the fix is one number in `memories.db`'s `PRAGMA user_version` (nothing else uses it there), read and written only through `MemoryStore` methods: 0 nothing done, 1 the rows are multiplied (set in the rows' own transaction), 2 the queue step has started (set under the queue lock before any queue file is rewritten, so 2 does not mean the files are done). A start-up that fails part way is run again from where the number says: the rows are not multiplied twice, and a queue step that failed before setting 2 starts again from the untouched files. With no `memories.db` both halves are skipped and the skip is logged. From after those skips until the step ends it shows the progress record of item 1 (phase "rescaling", no count), written before the checked open of the database and with no store opened for it; a step with nothing to do writes and removes it within moments. The factor, threshold, type list and the two progress numbers are named constants in `dev_constants.py`; the whole module goes with #388. Rows, queue entries or values that cannot be multiplied safely (NaN, a product that is not a finite number, text, a metadata or emotions that is not a mapping, an entry that cannot be written back unchanged) are left unchanged and logged by id.
9. **Check 25 cases and a helper script step.** The shift simulation file gains case (f) (the 30-day start gate counts from the oldest memory, proved both through `rebuild` and through `ensure_engine_ready`), case (g) (the self-model after an engine reset), case (i) (catch-up equals the uninterrupted run). The A1 timing script gains a `start` step.
10. **Wording and docs.** The heartbeat prompt segments lose their `memories_decayed` variable, `docs/maturity-manifest.md` no longer says the heartbeat decays emotions, one comment in `search_memories.py` says "edge decay and cleanup pass" so it cannot be read as the removed emotion pass (the Hebbian edge pass still exists). The module docstring of `brain/ingest/extraction_backfill.py` gave a stale reason for back-dating backfilled memories (not to reset `days_since_human`; that function now reads only the conversation files). Back-dating stays, and the docstring now gives the current reason: the creation time sets where the memory's feelings start fading (the engine fades from the later of creation and the switch-over), the memory's age for forgetting, and its recency in recall and dream seeding, so a months-old conversation dated now would come back as fresh, full-strength feeling and resist forgetting. Docstring only; `_newest_user_ts` is unchanged.
11. **One read of a memory's feelings.** `engine_utils.memory_feelings(memory, half_lives, switch_over_at, now)` returns a frozen `MemoryFeelings` (`feelings`: faded and held to 0-10, computed on first access; `peak`: the stored peak held to 0-10; `score`: as stored), and works with no engine running (pass None for all three inputs and nothing fades). The engine's public `memory_feelings(memory)` wraps it with the engine's own half-lives, switch time and clock. The per-name fade moved out of `faded_value` into one function, `engine_utils.faded_emotion`, which both use; `faded_value` now also holds its result to 0-10, so a stored negative reads as 0 on every path, and `_resolved_faded` calls the new read. Other readers and the field names are not changed here (Engine 7 #635 moves every per-memory reader to this one read).

## The start-up rebuild process (S107, S108, S109)

Added on 2026-11-17 after the second review, on the owner's decision that the one-shot rebuild is not run inside the bridge. Item 1 above describes what the rebuild does; this section describes where and how it runs. Code: `brain/bridge/daemon.py`, `brain/bridge/kill.py`, `brain/emotion/engine_files.py`, `brain/emotion/engine.py`, `brain/cli.py`.

1. **The rebuild subcommand.** `nell supervisor rebuild --persona NAME` is internal; the start spawns it. `cli._supervisor_rebuild_handler` refuses a missing persona directory first (exit 1, nothing written). It then writes the first "rebuilding" progress record before anything slow, sets up the runtime log (`runner._setup_runtime_logging`), calls `ensure_engine_ready(persona_dir)` unchanged, and removes the record in a `finally`. Nothing catches a failure: `main()` logs it to `cli-crash.log` and the process exits 1. It exits 0 on success, on the skip for an unreadable state with a failing integrity check, and on a roll-forward failure the engine logs and goes on from. It opens no store of its own and waits for an engine lock another process holds, one lock-wait step after another with no limit. A roll-forward (S108) needs no other build: `ensure_engine_ready` already runs the full recovery-mode rebuild for it.
2. **The need check.** `engine.start_rebuild_needed(persona_dir)` is True when the persona is not live (not switched over, no state, an unreadable state), else when `engine_rebuild.rolled_forward` says rows were written past the state. It takes no lock and writes nothing; it raises on a failed read. `daemon._rebuild_needed(persona_dir, bridge_running)` wraps it: with a bridge running it is only "the persona is not live", because a running bridge's own writes look like a roll-forward to the detector (the row is committed before the engine applies it), so a true roll-forward is found at the next start with no bridge running. A check that raises is logged to the runtime log and answers False, so the start goes on with the saved state.
3. **Command run records and the kill.** A real run of any of the six commands calls `engine_files.register_command_run` first (in `cli._engine_ready_or_refuse`, before the need check; a dry run writes none). It writes `command_runs/<pid>.json` (version, pid, pid token, persona) and removes it at exit with `atexit`, only if the record still names this process (`process_identity.is_own_identity`). `engine_files.live_command_runs` lists the other records. A record named for this process is left out by its file name. A record whose writer is dead is deleted. A record that cannot be read, is not an object or has no usable pid is decided by the pid in its file name: dead, deleted; alive, returned marked unreadable. A listing error raises `OSError`. `kill.kill_command(pid, token)` ends one command and its descendants. It creates the `psutil.Process` first, kills nothing unless `process_identity.matches` says the token is still alive, and answers `unknown_identity` for a missing token or an identity it cannot confirm. It shares `_end_tree` and `_release_tree` with `kill_bridge`, which now call the same two helpers. A command has no graceful stop to wait on, so it is ended at once; the bridge's own rule (no automatic hard kill after a stop request) is not applied to a command. Cost: the command's in-flight work is lost.
4. **Stopping the bridge.** `cmd_start` stops a running bridge first only when a rebuild is needed, which with a bridge running means the persona is not switched over yet (`_stop_for_rebuild`: `cmd_stop(args, reason=None, kill_pre_pr=False)`). A bridge with no identity token (one from an older version) is asked and waited for but never hard-killed here (`kill_pre_pr=False`; it is reported as not stopped after its short wait); for any other bridge the existing stop watch offers a hard exit only to a user in a terminal and never kills without one. A stop that does not finish ends the start before any rebuild, with one plain line on stderr and one line in the runtime log, and starts no bridge. An `attach` start (`nell chat`'s already-running branch) over a running bridge keeps the old refusal (exit 2) before any need check. A start over a running bridge with no rebuild needed is refused as before.
5. **The rebuild under the start lock.** `daemon._rebuild_under_lock` runs with the start lock held. It ends every live command record with `kill_command`; a command that is not ended (survivors, an identity that cannot be confirmed, an exception), an unreadable record whose pid may be alive, or a folder that cannot be listed ends the step with one plain line and exit 1, and nothing is rebuilt. A record with no token whose command was answered `unknown_identity` gets a line that also gives the record's path and says to delete it if that process is not a nell command. It then spawns `python -P -m brain.cli supervisor rebuild --persona NAME` and waits with no time limit. When stderr is a terminal it prints a start line and then the progress line when it changes (the same three forms as the window's: scale update, getting ready, "N of M (P%)"). Any exception, Ctrl-C included, kills the child, waits for it and propagates. A child that exits non-zero, or cannot be spawned, is one failed rebuild: one plain line and one log entry, and the step ends normally, so the bridge or the command goes on with the state saved before the rebuild. The lock has one release in a `finally` in `cmd_start`, which also covers a raise from the start-up steps after the lock (the log rotation, the stop-intent delete and the back-off reset). The need is asked again under the lock (the "re-check" below), so a starter whose need went away while it reached the lock ends no command for nothing.
6. **Where the step runs.** (a) `cmd_start`, after the persona check and the bridge stop, under the start lock, before the stop intent is cleared and the back-off reset (a failed start keeps both). (b) `cmd_run`, the OS-service start, after it holds the lock and passes its guard checks; a step that fails or raises notes a start for the back-off when the run is guarded, so the service manager's restart limit is not hit. (c) `daemon.run_rebuild_step(persona_dir)`, called by the six commands: with a bridge running it does nothing; otherwise, if a rebuild is needed, it takes the start lock without waiting. A start or rebuild already holding the lock refuses the command at once (exit 2, one line saying to try again when it has finished); this replaces the old 5 second wait on the engine lock. Otherwise it asks the need again under the lock, runs `_rebuild_under_lock`, releases the lock and starts no bridge; a command that cannot end another command exits 1. `nell chat` stops on either code like the other five. The bridge starts after the rebuild, on the rebuilt state, or on the saved state when the rebuild failed (the failure is logged). A bridge started around the supervisor (`python -m brain.bridge.runner`) starts on the saved state until the next supervisor start rebuilds.
7. **What in-process code went.** The bridge `lifespan`'s call to `ensure_engine_ready` (a short comment in `server.py` says why it is gone). Each command's in-process rebuild: `_engine_ready_or_refuse` registers and runs the step instead. The stop check and everything for it in `engine.py`: `_StoppedWhileWaitingError`, every `stop_requested` parameter, and the callable that `_locked_rebuild` took; it now takes `wait_for_lock: bool`, which the first rebuild and the roll-forward pass True and `recovery_rebuild` does not (it keeps its one wait and its failure). The commands' catch of a busy engine lock and its "busy with another job" line (added earlier in this review round) and `cli.py`'s `LockTimeoutError` import went with it: a command that meets a rebuild now meets the start lock first and is refused there. The names are in the removed-names test. The progress record, its readers, the timers and the app's display stay; the rebuild process now writes the record.
8. **The app's start waits (S109).** In the window's `/health` waits (`waitForHealth` in `app/src/lib/engineProgress.ts`), a status read that times out keeps the last real reading, and the wait's pause, only while that reading is under 30 seconds old (the wait's own limit, counted from when its answer arrived). After that the give-up clock runs again with what is left of its limit, and the display still shows the last reading. The Rust start wait (`wait_for_start` in `lib.rs`) is unchanged and keeps the previous reading on a timed-out read. A launch hold that a restart joined now resolves with the start's real outcome (`endEngineProgress(ok)` in `useRestartBridge.ts`).

9. **Who owns a record.** `process_identity.is_own_identity(pid, token)` says whether a record is this process's own: the pid is this process's and the token equals `own_token()`, and two missing tokens count as equal (a process that cannot read its own token records none, and the record is still its own). `EngineProgress._remove`, `state_file.update` and the run records' `atexit` removal use it, so a progress record written with no token is removed when its rebuild ends. The rebuild process, not the bridge, now writes and removes the progress record.

Related, not closed here: #754 (`nell migrate --install-as X --force` replaces the live persona folder without taking the start lock, so a rebuild running at that moment writes its state into the newly installed persona; the exposure exists on main and is outside this change) and #755 (`pid_is_alive` raises `OverflowError` on a pid too large for the OS and most callers let it escape; this change only guards its own new readers with `process_identity.is_pid_number`, in the run-record and progress-record readers of `engine_files.py`).

## Accepted edges

Each is commented in the code and in the commit notes.

- An install's first rebuild may count memories whose last-accessed time was stamped by a read that did not show them (old recall-resonance stamps and a few background reads fixed separately). A small nudge to the starting mood, mostly in the long average. Nothing waits on a fix.
- A hook that committed its memory before the rebuild's window read and applies after the rebuild's lock hold counts that memory twice (one extra entry).
- The x10 fix runs outside the engine lock. An older process (an old-code bridge or command running at the same moment) can still write a small row or a small candidate after the fix and before the switch-over, and an old-code claimed batch can be promoted at its old size. A row or queue entry written by something else while the app is down between the steps of a start-up (after the rows were done, or after the queue step read its files) is missed (the owner's ruling to use the version number for a half-finished repair accepts this). Because the number 2 is set before the queue files are rewritten, a crash or a failed write after it leaves that file's waiting candidates at the old, faint scale, and they are never multiplied twice (rewriting first and recording after would multiply a rewritten file again at the retry). This wording, "2 means the queue step started, not that it is done", differs from the wording the owner's earlier read-back was given, so it goes to the owner's review list. When every copy of the state is lost (missing) or unreadable the persona reads as not switched over and the first rebuild runs again at the next start (an unreadable one at the same start), recording a later switch-over time, but the x10 fix multiplies nothing then (its number is 2). Not decided here: an old-code bridge still running during the upgrade, holding a claimed batch in memory while a new-code process runs the switch-over (that batch is promoted later at the old scale).
- A state write that fails after the queue was emptied loses the queued chat changes (the showings are in the rows through `last_accessed_at`, the changes in the change log). When the failure is the I/O-fault skip above, each skipped start loses that start's queued changes this way. A recovery rebuild is not skipped: it raises, and the recovery job logs once per active day and retries at the next idle pass.
- A fresh process rebuilding a lost state folds each memory's stored values unfaded and restarts the fade clock at the rebuild, so the mood reads stronger than it was until the averages work it off (on the owner's review list; no data is lost or corrupted).
- A recovery rebuild from rows can replace a readable backup's snapshot when the main file is bad, and shift history.
- The queue copy of the x10 fix keeps every other line as the shared reader yields it, so blank lines, a CR before the newline and a leading BOM are not kept; a torn last line gains its newline. The queue's lock waits without a timeout (as every queue writer's does), so a stuck holder delays start-up.
- Stored negative feelings outside the x10 selector (a row whose strongest value is 1 or more) stay as they are: the engine holds them at 0.0 when read, and a one-time pass over every stored row was the rejected alternative. The writers of negatives are covered by a separate issue.
- Dev personas made by an earlier build of this branch (rows marked, number 0) would be multiplied again; that build never left the branch, so they are test data to recreate.
- A stored negative feeling folds as a real 0.0 entry at full weight and pulls both averages toward 0 (`resolve_emotions` holds a stored value to 0-10, then `_fold_average` folds it like any other entry); whether to keep that or leave negative entries out of the fold is posed to the owner separately and is not part of this change.
- `is_live` for a persona that is not switched over goes through the engine's cached state read: one stat when a state from the main file is cached, a walk of the main file and its backups on every call when no state file exists yet. Not measured on the record host.
- A persona that `ensure_engine_ready` left not live (an unreadable state with a `memories.db` that fails its integrity check, or a `RebuildStateWriteError` on an unreadable state) gets no fading until a later start succeeds, because `faded_emotion` returns the stored value when `switch_over_at` is None and nothing else fades it. It takes two faults together (they can share a root, such as a full disk), which is rare but not measured. The stored feelings stay as they were, slightly stronger than a fade would leave them; nothing crashes. The only loss is the one the state-write accepted edge above already names (in the write-failure case each skipped start loses that start's queued changes); the integrity-check case writes nothing. A fix needs a fade rule that is not decided yet, and fading from `created_at` instead would fade a value stored before the switch-over twice and add a second fade path. Accepted as a transient fault-state edge (HR4, P4); commented at `faded_emotion`.
- A start waits for ever for an engine lock held by something that is not a rebuild: a hung hook or drain, or an MCP server run by hand outside the product, at the moment of a start (a reading of well under 1 in 10,000 starts, not measured). The rebuild process shows its "rebuilding" record, also on a first switch-over (written before each wait step, and again at the next step if it was removed or refused meanwhile), and waits with no stop check and no limit (the owner's ruling: the start-up waits until the rebuild is finished); the start waits for it. Accepted (HR5 (7) as narrowed by S107, P4, R2); commented at the wait loop in `_locked_rebuild`.
- Two rebuild processes in the x10 step inside the same few milliseconds both find no live progress record and both write one, the later replacing the earlier. Starts hold the start lock, so this needs a child left by a dropped start still running when the next start's child begins. No crash, freeze or data loss, and no daemon kill (the readiness wait begins after the rebuild, and the starter waits for its child with no limit). If the record's writer ends first, the other child shows no record until its next write (once its x10 step ends, the rebuild writes one at the top of every pass of its lock wait, so the gap is the x10 step's length); the app's start wait (`wait_for_start` in `lib.rs`) drops the start only after 60 seconds with none, which ends the start command, not the child, and at launch on an unconfirmed overlay a failed start reaches `recoverUnhealthyBrain` and undoes the update. It needs an orphaned child and a new one inside the same milliseconds on the first start after the update that brings Engine 6 (well under 1 in 10,000 starts, not measured); closing it needs a lock around the record, which is disproportionate. Accepted (HR5, P4, as narrowed by S107); commented at the x10 step in `nudge_scale_fix.scale_up_small_feelings`.
- Roll-forward (a persona rolled back to an older brain and forward again; start check in `EmotionEngine._roll_forward`), edge (i): the recovery-mode rebuild it runs has the regular rebuild's losses: history and snapshot older than the 30-day window, and queued chat changes with no change-log line (the queue is emptied before the verified write, so a roll-forward whose write fails loses that start's queued changes too).
- Roll-forward, edge (ii): stored feelings the older brain's heartbeat lowered are faded again, so those rows read lower until they age out of the averages.
- Roll-forward, edge (iii): old-scale small values the older brain wrote are not multiplied again (the x10 fix's progress note says it is done).
- Roll-forward, edge (iv): a rowid is reused when the newest row is deleted (no AUTOINCREMENT) and a repair or restore can renumber rows, so a row then written at or below `rows_through` is missed.
- Roll-forward, edge (v): a state whose `rows_through` is unset (an older file, or a first rebuild with an empty window) skips the check until the first commit writes it; a roll-back in that gap is missed.
- Roll-forward, edge (vi): an engine save made before the check runs moves `saved_at` and `rows_through` past the roll-forward rows (a command-line command that writes memories without the engine-ready step). The same holds for the writers that do not fold (the migrator, recovery, the emergence kit, the consolidation gate's own write, written so that they are not folded and carrying their own older `created_at`), a failed direct apply (the next rebuild folds it), and a batch where one event folds and another's fold raises (only the folded row's rowid counts).
- Roll-forward, edge (vii): a failed check or rebuild followed by a direct apply before the next start moves `rows_through` past the roll-forward rows, so the start check does not fold them; a later rebuild inside the 30-day window does.
- A brain built from main before Engine 6 merges runs a shadow engine that rewrites the state without `switch_over_at` or `rows_through`. A persona rolled back to it and forward again reads as not switched, so the first rebuild runs again and records a new switch-over time, which restarts the fade clock: the rebuilt mood reads stronger than her real state for a while. Nothing durable records the original switch time. No published release has the shadow engine.

The thirteen below are new with the start-up rebuild process (see that section). Each names where it is commented in the code.

- A persona whose rebuild keeps failing or skipping (an unreadable state with a failing integrity check) is needed at every start. Each start with no bridge running repeats the rebuild process (twice for a service-managed persona: the start's step, then the service run's) and goes on with the saved state; each of the six commands run with no bridge running repeats it and goes on; a plain start over a running healthy bridge on such a persona stops it and starts it again, losing its in-flight work. Each such run first ends every other running command, a `nell chat --no-bridge` session included. A command that goes on after a failed rebuild runs on a state that may lag until the next start retries. Each run logs why. Commented in `_rebuild_under_lock` (`daemon.py`).
- `nell supervisor stop` typed while the start's rebuild step runs finds no bridge, returns 0, and the start then launches the bridge. Commented in `_rebuild_under_lock` (`daemon.py`).
- The app drops a start after 60 seconds with no rebuild progress record (`wait_for_start`, `kill_on_drop`). The stop runs inside that same `nell supervisor start`, so the drop ends the stop's watch too (the stop writes no progress record, so the 60 seconds are not paused) and can leave a pre-PR or unhealthy bridge half-stopped, with no rebuild and no new bridge, until the next start repeats the stop. No data is lost; at launch on an unconfirmed update a failed start reaches `recoverUnhealthyBrain` and undoes the update. Commented in `_stop_for_rebuild` (`daemon.py`).
- A stop that answers 0 while a bridge is somehow still there is not caught by the start's stop: a live bridge holds the start lock, so the start's lock refuses with exit 2. Commented in `_stop_for_rebuild` (`daemon.py`).
- A failed stop can print two lines (the stop's own, then the start's). Commented in `_stop_for_rebuild` (`daemon.py`).
- A queued service run that wakes between the start's stop and its lock takes the lock: that start returns 2 and the service run does the rebuild. Commented in `_stop_for_rebuild` (`daemon.py`).
- A roll-forward need under a running bridge is never acted on by a start (the bridge is stopped only when the persona is not switched over), because the detector cannot tell the bridge's own writes from a roll-forward; it is found at the next start with no bridge running. The alternative, stopping a healthy bridge whenever a start is typed over it inside that window, was rejected. Commented in `_rebuild_needed` (`daemon.py`).
- `kill_command` installs no signal handler: Ctrl-C resumes or finishes the tree through its `finally`, but SIGTERM or SIGHUP end the starting process at once and leave a tree that was already frozen stopped until the next start's `kill_command` ends it; nothing is lost, the frozen processes only wait. On Windows the end code of a killed command is 0. Commented in `kill_command` (`kill.py`).
- A kill of the MCP server child (a descendant of a command's claude call) between its memory commit and its feelings hook leaves that memory saved without its feelings applied. The kill comes before the rebuild process starts, so a rebuild that then succeeds folds the row; one that fails falls under the existing failed-direct-apply edge. Commented in `kill_command` (`kill.py`).
- A run record that cannot be read, or a readable one with no token, whose pid was reused by an unrelated live process blocks starts until that process exits or the user deletes the file the start's line names. Commented in `live_command_runs` (`engine_files.py`).
- A person who runs one of the six commands by hand inside a shell spawned from another registered command: the start's kill then freezes every descendant of the outer command, the inner one included, so both stay stopped until ended by hand. No code path of the product does this; a walk of the caller's ancestors was rejected as new code for a case the product does not create. Commented in `live_command_runs` (`engine_files.py`).
- In the window's `/health` waits, a real rebuild whose status reads time out for over 30 seconds can end the wait early (the last real reading is kept for 30 seconds from when its answer arrived, then the give-up clock runs again; the display still shows the last reading). The Rust start wait is unchanged and keeps the previous reading on a timed-out read, so that case stays open there by the owner's rule that a start waits until its rebuild is finished. Commented in `waitForHealth` (`app/src/lib/engineProgress.ts`).
- A restart that joins the launch hold (`showEngineProgress` took it where no restart was running) and is told the start failed gets `false`, but the shared restart state is reset to idle, not "failed", because only a restart's own `run()` sets "failed"; the joiner shows no error. Low. Commented in `endEngineProgress` (`app/src/hooks/useRestartBridge.ts`).
